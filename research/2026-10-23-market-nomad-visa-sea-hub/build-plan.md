## Build & Data-Acquisition Plan

*Axis: how to source the data and ship an MVP that ranks, for a money-making digital-nomad + visa-logistics hub covering Thailand/SEA, built solo on Supabase + a static-generation layer. Research date: 2026-10-23.*

### (a) Data acquisition — places, cost-of-living, directory content

The directory's "places" layer (cafes, coworking, coliving, long-stay accommodation) can be bootstrapped almost entirely from open datasets, which is the single biggest advantage this project has over a from-scratch crowdsource. Three overlapping open sources exist, and the licensing differences between them matter a great deal for a commercial product.

**OpenStreetMap (OSM)** is the base layer underneath almost everything else. Cafes are tagged `amenity=cafe` and coworking spaces are typically `amenity=coworking_space` or `office=coworking` (verify exact tag usage on TagInfo before querying) [OSM Overpass/Taginfo practitioner writeups](https://towardsdatascience.com/fast-and-easy-way-to-dynamically-import-open-street-map-data-into-a-google-sheet-file-495a400ec25/) (accessed 2026-10-23, confidence: Medium, tier: Low). For a one-shot national seed, the practical approach is a Geofabrik regional extract — Geofabrik publishes Asia extracts at `download.geofabrik.de/osm/asia/`, and a Thailand-only subset can be cut from the Asia file with Osmosis; the Overpass API is better for testing and small bounding-box pulls but has historically returned incomplete data over country-scale boxes [Geofabrik / OSM community](https://community.openstreetmap.org/t/how-to-create-own-map-for-thailand/59347) (accessed 2026-10-23, confidence: Medium, tier: Low). The binding constraint is the license: **OSM data is ODbL 1.0, which is share-alike.** This is the most important licensing fact for this project and is covered in its own paragraph below.

**Foursquare Open Source Places (FSQ OS Places)** is the most commercially friendly bulk option. Foursquare released a base layer of 100M+ global points of interest with 22 core attributes, updated monthly, distributed as Parquet files on Amazon S3, explicitly for commercial use under **Apache 2.0** [Foursquare blog](https://foursquare.com/resources/blog/products/foursquare-open-source-places-a-new-foundational-dataset-for-the-geospatial-community/) (accessed 2026-10-23, confidence: High, tier: Established), confirmed still distributed in 2025 by [ClickHouse docs](https://clickhouse.com/docs/getting-started/example-datasets/foursquare-places) (accessed 2026-10-23, confidence: High, tier: Established). Apache 2.0 is a permissive code license (not a share-alike data license), so you may build a commercial directory on it, but you must keep the NOTICE/attribution (including the 2024 Foursquare Labs copyright line), include a copy of the license, and, when you modify records, state that you changed them with the date [Overture release notes](https://docs.overturemaps.org/blog/2025/09/24/release-notes/) (accessed 2026-10-23, confidence: Medium, tier: Primary). *Analysis:* Apache 2.0 is materially easier to comply with for a proprietary directory than ODbL, because it carries no share-alike obligation on the data you combine with it.

**Overture Maps Foundation** (Linux Foundation, backed by Meta, Microsoft, Amazon, TomTom) ships a global places theme that defaults to the **CDLA-Permissive 2.0** license; for CDLA-licensed data, no visible text attribution or logo is required on maps and visualizations, and the only hard obligation is that the license text travels with the data if you redistribute the raw data [Overture FAQ, via search summary + Simon Willison](https://blog.simonwillison.net/2023/Jul/27/overture-maps/) (accessed 2026-10-23, confidence: Medium, tier: Low). Critically, **not all Overture themes are CDLA** — themes derived from OSM are a "Derivative Database" and carry ODbL, so attribution must read `© OpenStreetMap contributors, Overture Maps Foundation` for those [OSM diary quoting Overture](https://www.openstreetmap.org/user/jacobwhall/diary/406979) (accessed 2026-10-23, confidence: Medium, tier: Low). *Confidence note: the Overture Places-theme license should be confirmed on Overture's own attribution/license page before shipping; secondary sources agree it is CDLA-Permissive but I did not read the primary license page directly.*

**Geoapify** is a managed API wrapper over OSM data, useful if you want live geocoding/place lookups rather than bulk files. Its free tier is 3,000 credits/day (1 credit per simple Places/Geocoding request) with up to 5 req/sec, but the commercial terms are stated inconsistently on Geoapify's own site: the pricing page labels the free tier **"Limited Commercial Use,"** while the homepage and FAQ say the free plan covers commercial use [Geoapify pricing](https://geoapify.com/pricing) (accessed 2026-10-23, confidence: Medium, tier: Primary). The first paid tier (API 10) is $59/month for 10,000 credits/day with unambiguous commercial use; free-plan users must display a "Powered by Geoapify" link and must retain OSM attribution because the underlying data is OSM/ODbL [Geoapify pricing + FAQ](https://geoapify.com/pricing) (accessed 2026-10-23, confidence: Medium, tier: Primary). *Analysis:* Geoapify inherits OSM's ODbL obligations, so it does not sidestep the share-alike question — it only sidesteps the ETL work.

**Cost-of-living data is the hardest licensing problem.** Numbeo's data is free only for personal, academic and journalistic use; any commercial or internal-business use requires a paid plan — the Advantage plan at **260 USD/month (single user)** or Premier at **560 USD/month (multiple users)**, or the Numbeo API [Numbeo Data License](https://www.numbeo.com/premium/commercial-license) (accessed 2026-10-23, confidence: Medium, tier: Primary). Numbeo's Terms of Use define a "Client" as any entity that has purchased the API or a paid service and cap Numbeo's total liability at USD 1,000 [Numbeo Terms of Use](https://www.numbeo.com/common/terms_of_use.jsp) (accessed 2026-10-23, confidence: Medium, tier: Primary). A third-party blog claims the API has Basic/Professional/Enterprise tiers, but I could not confirm API pricing from Numbeo directly — treat as a gap. *Analysis:* scraping Numbeo to avoid the fee is both a Terms-of-Use breach and a reputational/legal risk; the cheaper compliant path for an MVP is to publish a small amount of hand-collected or crowdsourced cost figures (the Nomad List model, below) rather than license Numbeo at $260+/month on day one.

Data-source options at a glance (places + cost + enrichment):

- **OSM via Geofabrik/Overpass** — free, global, rich tags; **ODbL share-alike + attribution**; best for the bulk seed if you accept ODbL. (confidence: High that it's ODbL)
- **Foursquare OS Places** — free, 100M+ POIs, monthly Parquet on S3; **Apache 2.0, permissive**, attribution/NOTICE only; best commercial-friendly bulk source. (confidence: High)
- **Overture Places** — free, Parquet; **CDLA-Permissive 2.0** for the places theme (OSM-derived themes are ODbL); minimal attribution. (confidence: Medium)
- **Geoapify** — managed OSM API; free 3,000/day with ambiguous "limited" commercial use, $59/mo for clean commercial; inherits ODbL attribution. (confidence: Medium)
- **Numbeo** — cost-of-living; **not free for commercial**, ~$260–$560/mo or API; strict ToS, $1,000 liability cap. (confidence: Medium)
- **Crowdsourcing / manual curation** — fills coliving, long-stay, neighborhood "vibe," and current prices that open datasets lack; the proven cold-start method for this exact niche (see Nomad List, MVP section). (confidence: Medium)

**The ODbL share-alike trap (critical).** If you build your directory *database* by adapting, modifying, enhancing or extending OSM data, you create a "Derivative Database," and ODbL's share-alike clause can require you to make that database available on the same open terms [OSM Foundation Licence & Legal FAQ](https://osmfoundation.org/wiki/Licence_and_Legal_FAQ) (accessed 2026-10-23, confidence: Medium, tier: Primary). Share-alike is triggered by *Public Use* of the derived database — if you never publicly distribute the database itself you owe nothing, and a *Produced Work* (a rendered map, a web page, an app UI built from the data) does not by itself force you to open the surrounding experience, though you must still attribute and, for the map data portion, share that data [OSM Foundation FAQ](https://osmfoundation.org/wiki/Licence_and_Legal_FAQ) (accessed 2026-10-23, confidence: Medium, tier: Primary). A "Collective Database" — OSM data kept as an independent dataset alongside your own independent datasets — is not treated as derivative [OSM Foundation FAQ](https://osmfoundation.org/wiki/Licence_and_Legal_FAQ) (accessed 2026-10-23, confidence: Medium, tier: Primary). *Analysis / design implication:* For a commercial site that wants to keep its enriched data proprietary, the cleanest route is to **build the core directory on Foursquare OS Places (Apache 2.0) and/or Overture's CDLA places theme, and treat any OSM data as a separate, attributed collective layer rather than merging it into one enriched master table.** This avoids the risk that your proprietary enrichment (prices, ratings, nomad notes) becomes something you must open under ODbL. This is a genuinely under-appreciated solo-founder trap and warrants a lawyer's read of ODbL 1.0 before launch if OSM is used as the spine. (These are community/FAQ summaries, not legal advice.)

### (b) The visa-rules dataset

There is **no official, openly licensed passport/visa API from Henley or the underlying IATA source.** Henley's own pages state the index is built on exclusive IATA (Timatic) data plus in-house research [Henley Global passport index about page](https://henleyglobal.com/passport-index/about) (accessed 2026-10-23, confidence: Medium, tier: Primary), which means the authoritative visa-matrix data is proprietary and IATA-sourced. The widely used community workaround is `ilyankou/passport-index-dataset` on GitHub: 199 countries of visa requirements in CSV (both matrix and tidy/long formats, with ISO-2, ISO-3 and name variants), values including visa-free (with day counts 7–360), visa-on-arrival, eta, e-visa, visa-required and no-admission, **released under the MIT license** [ilyankou/passport-index-dataset](https://github.com/ilyankou/passport-index-dataset) (accessed 2026-10-23, confidence: High, tier: Established). That repo was last updated 12 January 2025 and is now archived; data from February 2026 onward lives at `github.com/imorte/passport-index-data`, and the underlying data is scraped from passportindex.org (Arton Capital) [ilyankou/passport-index-dataset](https://github.com/ilyankou/passport-index-dataset) (accessed 2026-10-23, confidence: High, tier: Established).

*Critical caveat (flag for the user):* the MIT license on that repo covers the repo's code/compilation, but the underlying passport-index data is itself derived from Arton Capital's site which draws on IATA Timatic — so the MIT label does **not** cleanly establish that you have redistribution rights to the underlying facts for a commercial product. Facts (e.g., "US passport gets 180 days visa-free in country X") are generally not copyrightable, but a wholesale copy of someone's compiled database can raise database-rights and ToS issues. *Analysis:* for an MVP, use the open dataset to seed the generic tourist-entry visa matrix, but treat the money-making, differentiated content — Thailand/SEA **long-stay** visa logistics (DTV, Non-Immigrant O/O-A/O-X, LTR, Elite, education visas, border runs, 90-day reporting, extensions) — as **hand-maintained**, because passport-index-style datasets only cover short tourist entry and omit exactly the long-stay rules a nomad hub monetizes. That hand-maintained long-stay layer is both the legal-safe zone and the SEO moat (unique content).

Concretely for Thailand, the flagship long-stay product is the **Destination Thailand Visa (DTV)**: five-year validity, up to 180 days per entry extendable once by a further 180 days, a ~500,000 THB funds benchmark held for the prior three months, and a fee around 10,000 THB; it permits remote work for *foreign* employers/clients but not work for Thai companies or Thai clients [Royal Thai Embassy (Phnom Penh) DTV page](https://phnompenh.thaiembassy.org/en/publicservice/destination-thailand-visa-dtv) (accessed 2026-10-23, confidence: Medium, tier: Primary); embassy pages note some consulates restrict applications to residents of that country and require e-Visa filing ~21 working days ahead [Royal Thai Embassy (Singapore) DTV page](https://singapore.thaiembassy.org/en/page/dtv-visa-workcation) (accessed 2026-10-23, confidence: Medium, tier: Primary). *Conflict:* embassy pages say DTV holders cannot do freelance work for Thai clients, while several commentary sites describe it loosely as a "digital nomad visa" that allows remote work — the embassy wording is authoritative and the distinction (foreign clients only) is itself a high-value content point for the hub.

### (c) SEO structure for a places + visa directory

Google's post-2024 landscape makes the structure choice existential for a programmatic directory. In the **March 2024 core update Google introduced "scaled content abuse,"** defined as generating "large amounts of unoriginal content that provides little to no value to users, no matter how it's created" — the trigger is lack of value, *not* automation or templating per se [Google Search Central blog, March 2024](https://developers.google.com/search/blog/2024/03/core-update-spam-policies) (accessed 2026-10-23, confidence: High, tier: Primary). The same update added "site reputation abuse" and "expired domain abuse"; third-party monitoring reported 837 of 49,345 tracked sites (1.7%) were deindexed around it [Search Engine Journal](https://www.searchenginejournal.com/google-march-2024-core-update/506070/) (accessed 2026-10-23, confidence: Medium, tier: Established). *Analysis:* a places+visa directory survives this specifically because each generated page can carry genuinely unique structured data — a real coworking space with real amenities/prices, or a real nationality×destination visa rule with day counts and official source links — which is the opposite of the "minor variable swap" thin-content pattern that practitioners flag as the programmatic-SEO failure mode [dsebastien concept note](https://concepts.dsebastien.net/concept/thin-content) (accessed 2026-10-23, confidence: Low, tier: Low). The remedy every source converges on is "attach unique, substantive data to each page," and because HCU-type quality signals are assessed site-wide, a mass of thin pages can drag down the good ones [ProfileTree guide](https://profiletree.com/thin-content-and-seo/) (accessed 2026-10-23, confidence: Low, tier: Low) — so it is better to ship 300 genuinely rich pages than 30,000 near-empty ones.

For **URL/page architecture**, the natural, non-thin structure for this niche is a matrix of intersecting entities, each of which maps to a real query: per-city hubs (`/chiang-mai/`), per-category within city (`/chiang-mai/coworking/`), per-place detail pages (`/chiang-mai/coworking/<space>/`), per-visa guides (`/visa/thailand/dtv/`), and — the highest-unique-data pages — per-nationality×visa pages (`/visa/thailand/us-citizens/`, `/visa/thailand/dtv/for-germans/`). The visa matrix is especially SEO-defensible because every nationality page legitimately contains different facts (different day counts, different eligibility), so it is unique by construction rather than by template padding. Internal linking should connect each city to its visa guides and each visa page to the cities where that visa is most used, building topical clusters.

For **structured data**, use schema.org `LocalBusiness` (or a more specific subtype where one exists) on place pages — Google's own guidance is to use the most specific applicable type, supply required `name` and `address`, and validate with the Rich Results Test; `AggregateRating` stars are permitted only for genuine reviews actually shown on the page, and self-serving reviews are prohibited [Google LocalBusiness structured-data docs](https://support.google.com/webmasters/answer/3227699) (accessed 2026-10-23, confidence: Medium, tier: Primary). Visa guide pages benefit from `FAQPage`/`HowTo`-style markup and clear "last updated" dates for freshness signals. **Sitemaps at scale:** each sitemap file is capped at 50,000 URLs and 50 MB uncompressed, and a sitemap index (which can reference up to 50,000 sitemaps) is the standard way to split a large site [third-party guides citing Google](https://library.linkbot.com/what-are-the-url-and-file-size-limits-for-sitemaps-and-how-can-large-sites-adapt/) (accessed 2026-10-23, confidence: Medium, tier: Low) — a few thousand MVP pages fit in a single sitemap, so this only matters once the directory scales into the tens of thousands.

### (d) Stack — Supabase + static-gen (Astro vs Next.js)

Both frameworks can produce thousands of pages from a Supabase database; they differ in how they handle build time and data freshness. **Astro 5's Content Layer** is purpose-built for this: a "loader" is a plain async function (often just a `fetch` returning JSON, which can be a Supabase REST/RPC call) that runs at build time and populates typed content collections, which pages then read via `getCollection`/`getEntry` [Astro 5 release](https://astro.build/blog/astro-5) (accessed 2026-10-23, confidence: High, tier: Primary); the Content Layer was explicitly introduced as "the first step toward fast builds for sites with tens or hundreds of thousands of pages" [Astro 4.14 blog](https://astro.build/blog/astro-4140) (accessed 2026-10-23, confidence: High, tier: Primary). **Next.js** handles scale differently: `generateStaticParams` defines which paths are prebuilt, and ISR lets you prebuild only a subset and server-render the rest on first request ("if a request comes in for a path that hasn't been generated, Next.js will server-render the page on-demand"), with `dynamicParams` controlling unknown-path behavior and on-demand revalidation for updates [Next.js ISR docs](https://nextjs.org/docs/app/guides/incremental-static-regeneration) (accessed 2026-10-23, confidence: High, tier: Primary). The key trade-off Vercel itself states: with pure SSG "build times scale linearly with the number of pages," so very large sites can take hours — which is exactly the problem ISR and Astro's incremental builds exist to solve [Vercel ISR blog](https://vercel.com/blog/how-hashicorp-developers-iterate-faster-with-isr) (accessed 2026-10-23, confidence: Medium, tier: Established).

On **build speed**, a single practitioner benchmark of a 1,000-page docs site reported ~18s for Astro vs ~52s for Next.js, but this figure recirculates across comparison blogs from one test and should be treated as a single data point, not a benchmark [eastondev comparison](https://eastondev.com/blog/en/posts/dev/20251202-astro-vs-nextjs-static-site/) (accessed 2026-10-23, confidence: Low, tier: Low). The consensus across comparisons is that Astro wins for content-first sites (docs, directories, blogs) while Next.js wins when you need heavy server logic, auth, and ISR's incremental freshness [Contentful comparison](https://contentful.com/blog/astro-next-js-compared) (accessed 2026-10-23, confidence: Medium, tier: Established).

**Supabase as the data source** works in both. Supabase's own Astro quickstart queries inside page frontmatter (compatible with build-time fetching), requires tables to be exposed via the Data API, and enables Row Level Security by default [Supabase Astro quickstart](https://supabase.com/docs/guides/getting-started/quickstarts/astrojs.md) (accessed 2026-10-23, confidence: Medium, tier: Primary); Astro's official Supabase guide is written around on-demand/server rendering for auth endpoints (`export const prerender = false`), so note that auth flows need a server adapter even on an otherwise-static site [Astro Supabase guide](https://docs.astro.build/en/guides/backend/supabase) (accessed 2026-10-23, confidence: Medium, tier: Primary). Supabase is Postgres, so it brings native full-text search (`tsvector`, `pg_trgm`) and PostGIS geospatial queries for "coworking near me" / radius filters — standard Postgres features, though I did not find a source specifically walking through them for this use case (treat as inferred). **Search/filter UX:** for an MVP of a few thousand places, a client-side filter over a prebuilt JSON index is simplest and fastest (no server round-trips, works on a static host); as the dataset grows past what's comfortable to ship to the browser, move filtering to Supabase REST/RPC calls (PostgREST) or a dedicated search service. *Synthesis / recommendation:* for a solo founder optimizing for SEO page volume and low ops, **Astro SSG with the Content Layer pulling from Supabase at build time, deployed to a static/edge host, with client-side filtering for the MVP** is the lower-complexity choice; reach for Next.js ISR only if the directory data changes so frequently that full rebuilds become the bottleneck, in which case ISR's on-demand regeneration is the deciding feature.

### (d2) PWA or mobile wrapper — is it worth it for the MVP?

The brief describes this as "software," not only a website, so the question is whether to ship an installable app on day one. On iOS, web push has worked since iOS 16.4, but only for a PWA installed to the home screen: a Safari tab cannot receive push even when the user grants permission [MagicBell PWA iOS guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide) (accessed 2026-10-23, confidence: Medium, tier: Low). Practitioner guides list further iOS limits: no automatic install prompt, weaker offline storage persistence and background processing, and no App Store listing [MobiLoud PWA iOS guide](https://www.mobiloud.com/blog/progressive-web-apps-ios) (accessed 2026-10-23, confidence: Medium, tier: Low). Ionic, which makes Capacitor, says the same web codebase can ship as a native iOS app unchanged [Ionic blog](https://ionic.io/blog/a-note-on-ios-17-4-and-pwas) (accessed 2026-10-23, confidence: Low, tier: Established, vendor claim). The catch is that a bare web-view wrapper is the most common App Store rejection under Apple's minimum-functionality rule, so a wrapper needs real native features such as push, offline mode and native navigation [vp0 blog](https://vp0.com/blogs/convert-pwa-to-ios-app-fast-2026.md) (accessed 2026-10-23, confidence: Low, tier: Low). One developer reported on Apple's forums that push failed when Capacitor loaded a remote `server.url` but worked with a locally bundled build [Apple Developer Forums](https://developer.apple.com/forums/thread/789719) (accessed 2026-10-23, confidence: Low, tier: Low, single report).

*Analysis:* the MVP should not ship a mobile app. Discovery for this product happens through search, Reddit and Pinterest, and every one of those lands on a web page. An app has no SEO value, adds store review and maintenance, and risks rejection if it's a thin wrapper. What's worth doing cheaply is making the Astro site an installable PWA (a manifest plus a service worker that caches the user's saved city guide and the visa calculator for offline use). That costs about a day and serves nomads with patchy connections at borders. The one feature that would justify an app later is a retention loop with notifications, such as DTV 180-day stay countdowns, 90-day reporting reminders and extension deadlines. Even that can launch as installed-PWA push first. A Capacitor wrapper only makes sense once paying users ask for those reminders and iOS PWA install friction shows up as lost conversions, which might be 6–12 months after launch.

### (e) MVP scope — smallest version worth shipping

The directly relevant precedent is **Nomad List**, which cold-started in 2014 not as a site but as a *public Google spreadsheet* that crowdsourced data via Twitter; contributors spontaneously added columns (safety, LGBTQ-friendliness, coffee-shop density), and Pieter Levels then built a minimal site on that data, in public, with plain HTML/CSS/JS and a PHP/SQLite backend, monetizing through a paid community that began on Slack [levels.io / Starter Story breakdown](https://www.starterstory.com/stories/nomad-list-breakdown) (accessed 2026-10-23, confidence: Medium, tier: Low). *Analysis:* the lesson for solving the chicken-and-egg problem is that the data seed came first (a spreadsheet anyone could fill), the directory second, and the money (membership) third — manual curation and visible building-in-public substituted for having no users.

The smallest version worth shipping here is **one city + one visa flow, done to genuine depth**: a Chiang Mai nomad guide (coworking, cafes, coliving/long-stay, neighborhoods, cost-of-living snapshot) plus a single high-intent visa tool — the **DTV eligibility/stay calculator** (funds check, 180-day-per-entry tracker, extension logic). Chiang Mai is the canonical Thai nomad hub and the DTV is the current flagship long-stay route, so both ride existing search demand. Seed the places layer from Foursquare OS Places / Overture (commercial-safe), enrich by hand for the ~50–150 venues that actually matter in Chiang Mai, and hand-write the DTV content against embassy sources.

MVP scope / compliance checklist:

- **One city (Chiang Mai), ~100 curated venues** seeded from Foursquare OS Places (Apache 2.0) or Overture CDLA; keep OSM separate if used, to dodge ODbL share-alike.
- **One monetizable visa flow (DTV)**: eligibility checker + 180-day stay/extension calculator, content hand-written from Royal Thai Embassy pages with "last updated" dates.
- **Unique structured data per page** (real amenities, prices, visa day-counts) with schema.org `LocalBusiness` + `FAQPage`; validate in Rich Results Test; avoid thin templated pages (scaled-content-abuse risk).
- **Attribution done right**: Foursquare NOTICE + Apache license text; OSM/Geoapify "© OpenStreetMap contributors" (+ "Powered by Geoapify" if on its free tier); no Numbeo data unless licensed.
- **Cost-of-living seeded manually/crowdsourced**, not scraped from Numbeo (ToS + liability risk).
- **Stack**: Astro Content Layer + Supabase build-time fetch, client-side filtering, single sitemap (<50k URLs), static/edge deploy.
- **App surface**: installable PWA only (manifest + offline cache for the saved city guide and the DTV calculator). No App Store app in the MVP. Consider a Capacitor wrapper later, for visa-deadline push reminders, if iOS install friction shows up in conversions.
- **Realistic solo timeline (analysis, not sourced):** a credible estimate is roughly 4–8 weeks to a shippable Chiang Mai + DTV MVP — ~1 week data ETL/seed, ~1–2 weeks venue curation + visa content, ~2–3 weeks build/templates/schema/filtering, ~1 week polish/sitemap/launch. Flagged as the author's inference, not a sourced figure.

### (f) Non-Google distribution to cold-start traffic

Because a new directory has no domain authority and Google indexing is slow and penalty-prone, early traffic should come from channels that don't depend on ranking. **Reddit** is high-intent for this niche but hostile to promotion: r/digitalnomad's moderators state outright it "is not a community full of potential people to market to," and the site-wide norm is the ~10% self-promotion guideline with individual subs enforcing stricter ratios — the workable pattern is "lead with value," i.e., post genuinely useful answers/guides and let the link be secondary [Reddit self-promotion guides + r/DigitalNomad sidebar](https://redship.io/blog/reddit-self-promotion-rules-2026) (accessed 2026-10-23, confidence: Medium, tier: Low). **Pinterest** is the strongest evergreen driver for travel content: pins are searchable and persist for months-to-years and surface in both Pinterest and Google results, with travel bloggers self-reporting 40k–90k monthly pageviews from the channel — though these numbers come from promotional/vendor sources and should be discounted [Travelpayouts / jessieonajourney](https://travelpayouts.com/blog/how-to-use-pinterest-to-promote-a-travel-blog/) (accessed 2026-10-23, confidence: Low, tier: Low). The practical tactics are themed boards per city/visa topic, keyword research in Pinterest's own search/Trends, and multiple pin variants per page. **YouTube** and established nomad communities (Facebook groups, nomad Slack/Discord, the Nomad List community itself) are the other obvious channels, but I found no niche-specific sourced data on YouTube cross-promotion for Thailand nomad content — treat as a gap. *Synthesis:* the Nomad-List-style "build in public" on X/Twitter plus value-first Reddit answering plus Pinterest's evergreen pins is the realistic solo cold-start stack while SEO compounds; none of these require ad spend.
